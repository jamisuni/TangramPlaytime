# WO-002 — #Content: the puzzle library in `:content` behind `IPuzzleLibrary`

**Status:** Done (closed 2026-10-11 15:45, G4 under governance row 9 `ai`)  ·  **Mode:** Full (b)
**Kicked off by:** Jami / 2026-10-11 (KICKOFF.md paste-in brief)  ·  **Plan approved:** 2026-10-11 14:51 (G3 under governance row 7 `ai`; plan-check GREEN; plan review 0 B after one recirculation)

## Goal

Build the puzzle library every screen reads: the thirteen `Tangrams/*.json`
files shipped inside `:content`, the `tangram-puzzle/1` parser
(kotlinx.serialization, ADR-004), the load-time validity check (REQ-038's
rules — the build-side oracle ADR-004 names) and the ‹ › order kind → rating
→ id, as the `IPuzzleLibrary` implementation (locked tier: implement, never
change). Second in the owner's order because #Solving (WO-003) and #Browsing
(WO-004) both ask this seam for their puzzles, silhouettes and titles. The WO
also re-judges the authoring tool's corner rule (`tools/tangram_geom.py`
`outline_corners`, and the V11 build-order line it feeds) against the
contiguity rule the kernel implements — a project-tool fix, not a Contract
change (`design-inputs.md` §2 item 13).

  A1), #PuzzleOrder (REQ-040 A1..A2), #PuzzleWarmups (REQ-041 A1..A2),

## Mode

Chosen: **Full (b)** — a governed interface is touched: `IPuzzleLibrary`
(locked tier, with the `tangram-puzzle/1` format) is implemented for the
first time. Reason **(a)** was considered and is **not claimed**: `:content`
is not a new module — its Gradle skeleton (`content/build.gradle.kts` with
the Android library and serialization plugins, a placeholder `Content.kt`
and `ContentScaffoldTest`) exists and compiles since P2 (`.swdev/run-log/P2-skeleton.md`).
What needs a design is the shape behind the seam: how the thirteen files
reach the module and are read on both the JVM and the device, where the
piece-congruence geometry comes from, and what the load-time check rejects.

## Constraints & notes

- `IPuzzleLibrary.kt` and `Tangrams/puzzle.schema.json` are locked (guard
  `contract_paths.locked`); the puzzle files themselves are not — but no
  puzzle file is edited in this WO (owner rule 7 would then require the
  validator + renderer + a look at the sheet). The library never exposes
  file paths, JSON or a parsing type across the seam (KDoc "must never").
- **Value rules once (D1, architecture.md §1 note: TYPE-001 lives in
  `:kernel`) vs. piece congruence in `:content`.** The validity check needs
  the five piece shapes. The design must resolve this through the seam
  (`:content` consumes `ILockEngine.vertices` — then `:content` depends on
  `:kernel` only for the engine object the app wires in, and the JVM test
  uses the real engine) **or** justify a content-side shape table with the
  REQ that requires it (the format's §3 table is the authoring tool's, DI-5).
  A dependency of `:content` on `:kernel`/`ILockEngine` is a `build-map.md`
  cross-feature-deps change (notify tier — a logged contract-delta,
  summarised below). Whatever is chosen, `:content` product code keeps G-12:
  no reaching into another module's internals.
- **Readable on the JVM.** Whatever carries the thirteen files into the
  module (Android assets, classpath resources, a Gradle source-set include of
  `Tangrams/*.json` at build), `:content testDebugUnitTest` must load every
  shipped puzzle **through the same reading path the app uses**. If the
  design's reading path cannot be exercised on the JVM (an `AssetManager`
  behind a `Context`), the WO gains a device task and the two device
  channels are added here at G3 before P4 — both are proven (P2 run log).
- Expected outcomes are sealed results or the KDoc's `null`, never
  exceptions (G-15); a puzzle file that fails a rule is a **build defect**
  the load-time check must surface (the library "must never list a puzzle
  that fails the validity rules") — the design says how (fail fast at
  load vs. drop the file), named in a `decisions.md` row.
- The `tools/` fix: `outline_corners` classifies a vertex by the contiguity
  of the covered directions (interior = full 360°, straight side = one
  unbroken 180° arc, anything else a corner — `designs/WO-001-design.md` §2
  `Silhouette`), so `shapes-warmup-4` (2,2) becomes a corner and the V11
  build-order line (which seeds its anchors from `outline_corners`) agrees
  with the kernel. Exact ℚ(√2) arithmetic stays. Acceptance for the tool:
  `python tools/validate_puzzles.py Tangrams` still 13/13 valid with a
  complete build order each; `outline_corners` of warmup-4 includes (2,2)
  and is unchanged on the other twelve (the design review's F1 scan:
  "same corners as `tangram_geom.py` everywhere plus (2,2) on warmup-4").
  A Python check under `tools/tests/` is a tool test, not acceptance
  coverage (test_globs scan `*/src/test/*` only).
