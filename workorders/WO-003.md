# WO-003 — #Solving: the Play screen in `:play` (board, tray, gestures, preview, solved picture)

**Status:** Done (closed 2026-10-12, G4 under governance row 9)  ·  **Mode:** Light
**Kicked off by:** Jami / 2026-10-11 (KICKOFF.md paste-in brief)  ·  **Plan approved:** 2026-10-11 17:17 (G3 under governance row 7 `ai`; plan-check GREEN; plan review 0 B / 3 S)

## Goal

Build the one screen the player lives on: the empty silhouette board, the
fixed tray of miniatures with its size marks and flip badge, the drag with
its landing preview, tap-to-turn, the two-finger twist, the mirror of the
parallelogram, the go-home return, the corner pulse of a mini puzzle and the
solved picture — in `:play` (Jetpack Compose), asking `ILockEngine` for every
position and `IPuzzleLibrary` for every puzzle, wired by `:app`
(`PuzzleLibraries.bundled(LockEngine())`, WO-002 design review F4). Third in
the owner's order: the lock engine (WO-001) and the library (WO-002) exist,
and every later WO (#Browsing, #DevTools, #Layout, #PlayTime) decorates this
screen. **The first WO with device tests**: the floor image is a G3
precondition and the release verifier arrives with it
(`platform-notes/android.md`). Persistence is WO-004's: the screen holds its
state in memory this WO, behind a seam WO-004 fills with `IProgressStore`.

## Constraints & notes

- **Seams (G-12, O-01..O-07).** `:play` main code depends on `:contracts`
  only; `:app` constructs `LockEngine()` and `PuzzleLibraries.bundled(engine)`
  once per process and hands both to the screen. No geometry in `:play`: the
  piece corners for every drawing come from `ILockEngine.vertices`; the drop
  and the landing preview both call `findLock` (REQ-021 rule: the same
  search, at most once per displayed frame); a board tap calls
  `tryTurnInPlace`, the board badge `tryMirrorInPlace`; `isSolved` after each
  lock; `outlineCorners` for the pulse. Strings are `:app` resources with an
  `en` and a `fi` value (G-10, O-06; the Finnish wording is a reference
  translation → `review-notes.md`). Sound and haptics: `:play` exposes the
  O-07 events (`PickedUp`, `Turned`, `Locked`, `WentHome`, `Solved`) and plays
  nothing (WO-007).
- **In-memory state behind the seam (WO-004 fills it).** The screen's state
  holder keeps, per puzzle id, the TYPE-006 state and the board placements in
  memory; it is shaped so that WO-004 replaces the memory with
  `IProgressStore` without reshaping the screen — but nothing of the store is
  pre-built (D4). A tray piece's turn or mirror is not part of that state
  (decisions.md 2026-10-11, F36).
- **Draw in pixels (G-17).** Every board and tray path is built in px from
  unit vertices × the current scale; no path is drawn under a canvas
  `scale()` (the floor image blurs it). The silhouette is one flat colour
  with no inner line (REQ-011): the solution polygons are merged into one
  path (a path union, or one path with non-zero winding — the implementer
  proves on the **floor image** that no anti-aliasing seam shows between
  neighbouring solution pieces). The solved picture is clipped to that same
  path (REQ-023 A1, REQ-039 A1; the `ArtLayer` KDoc).
- **Gestures (REQ-014..018).** Tap = a touch that ends having moved < 12 dp,
  whatever its duration (REQ-015) — Compose's `detectTapGestures` applies a
  long-press timeout, so the classification is written on raw pointer events.
  A board piece's touch area is its shape grown by 12 dp; a tray piece's is
  its whole cell (REQ-015 rule); the flip badge's 60 dp area wins inside the
  parallelogram's cell (the natural reading; pending
  `chg-draft-req018-badge-touch-precedence.md` — a decisions row, not a
  Contract text). While a piece is dragged, every further touch is a twist
  finger for that drag (pending `chg-draft-req017-second-finger-never-a-tap.md`,
  same treatment); step boundaries at ±22.5°, ±67.5° … of the second finger's
  starting angle; lifting it keeps the turn. A drag ended by anything other
  than a release (a cancel, the activity stopping) is a missed drop
  (`chg-draft-req020-interrupted-drag.md`, decisions row; no token).
- **Timings are the REQs' rules:** grow to board size within 120 ms
  (REQ-014), lock glide 180 ms (REQ-019), go-home 180 ms (REQ-020), picture
  fade 800 ms starting 600 ms after the last lock, confetti 2.4 s (REQ-023),
  pulse about 600 ms (REQ-051); the floating offset 30 dp phone / 40 dp
  tablet (REQ-014 ASSUMPTION). Reduced motion (REQ-023, REQ-051): no pop,
  confetti or pulse animation, the picture and the corner markers still
  appear — read from the system's animator duration scale (0 = removed
  animations; no permission). Animations run on Compose's frame clock; a
  device test drives it through the compose rule's main clock, never a
  sleep (platform-notes).
- **Device tests.** Compose UI tests in `play/src/androidTest` (the screen
  with a test library and the real `LockEngine` as test dependencies) and
  the `:app` launch test in `app/src/androidTest` (the real wiring: the
  bundle read on the device, WO-002 code review N4; the opened puzzle on a
  fresh start). Semantics: every tray cell, board piece, the badge, the
  preview, the picture and the pulse carry test tags the planner names;
  tagged containers merge their descendants (platform-notes § Compose test
  kit). Pure logic — tap/drag classification, twist step counting, the
  REQ-013 cell arithmetic, the state holder's transitions, the REQ-002 A1
  solve of every bundled puzzle — is JVM-tested in `play/src/test`.
- **The release verifier** (`platform-notes/android.md`, G-01, G-08):
  `.swdev/verifiers/v01_release_apk.py` (≤ 150 lines, budget 1/WO) builds
  nothing itself; it reads the release APK the close step builds and checks
