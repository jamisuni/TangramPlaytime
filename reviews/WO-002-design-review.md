## Findings

### F1 — CONTRACT · Should · §2 `PuzzleParser.parse` (`PLACEMENT`), `decisions.md` row 47
- **Observation:** The locked format admits a solution entry as `piece` + `rot`/`flip`/`at` (schema `placement.oneOf`, Spec §2); the design reads only `polygon`. That narrowing is recorded in `decisions.md` row 47 but appears nowhere in the design itself (§2 says "`PLACEMENT`: `polygon`, 3–4 points"; §3 is silent), so a reader of the design cannot see that a format-valid file fails the build. Row 47 also says the other form "is a `PLACEMENT` violation", but with the DTO as designed (no `rot`/`flip`/`at` fields) and the default `Json` (`ignoreUnknownKeys = false`, verified R4) the unknown keys throw `SerializationException` before any rule runs — the kit would see `JSON`, not `PLACEMENT`. The authoring validator (`validate_puzzles.py` `load_solution`) accepts the `at` form and set-equal polygons, so it and the loader now disagree on two things.
- **Proposed resolution:** State the narrowing in design §3 (library facts / must-never) with row 47's reasoning. Make the rule attribution true: declare `rot`, `flip`, `at` as optional DTO fields and reject their presence as `PLACEMENT` with a detail naming the unsupported form (or correct row 47 to `JSON`). Carry the validator divergence (at-form, V3 set equality) as a tools follow-up for the content batch WO — not in this WO's scope.

### F2 — TEST · Should · §4 "Kit staging", TASK-005/TASK-006, `Rule`
- **Observation:** The kit enters the tree after TASK-005, but its geometric rejections (`CONGRUENT`/`OVERLAP`/`CONNECTED`/`WARMUP`, tokened REQ-038.A1 and REQ-041.A2) cannot be green until TASK-006. For "shipped-file tests green after TASK-005", TASK-005's `PuzzleLoader` must ship a version that skips geometry — a second loader shape that TASK-006 then rewrites — and the `Rule` enum carries four entries no code raises at that step. The plan reviewer's rule is that every done-check is green at its step.
- **Proposed resolution:** Either merge TASK-005 and TASK-006 (`ValidityCheck` + `Edges` are small, and the loader then has one shape — D2), or have the planner stage the kit in two files, the geometric file landing with TASK-006 and REQ-007.A1's token on the post-TASK-006 run. The planner decides; the design should say which.

### F3 — QUALITY · Should · §3 "Proof", TASK-004 done-check
- **Observation:** The proof names only `app-debug.apk`; the WO-close release verifier runs on the release APK, and a Java-resource path that works for debug but is stripped for release would pass the stated done-check and fail at close. Re-derived here: the release AAR `classes.jar` and `app-release-unsigned.apk` both carry the 14 entries with the design's wiring (R1), so the risk is closed in fact but not in the task's evidence.
- **Proposed resolution:** Add the release artifact to TASK-004's done-check — `:content:bundleReleaseAar` and a listing of `classes.jar` (14 entries under `app/tangramplaytime/content/puzzles/`) — so the evidence covers the build type the verifier checks.

### F4 — TRACE · Should · §1 "How it works" step 2 vs. §4 cut
- **Observation:** §1 says "`:app` calls `PuzzleLibraries.bundled(LockEngine())` once", and §3 says "build the library once (WO-003)", but no task in the cut delivers or explicitly excludes the `:app` wiring. The planner could look for it, or a later WO could assume it was done here.
- **Proposed resolution:** One line in §4: the `:app` wiring of `bundled(...)` is deliberately not touched in WO-002 and belongs to the WO that first consumes `IPuzzleLibrary` on screen (WO-003), with the note that the library is built once per process.
